# Development notes

The git log tells you when code landed. This file tells you how the
project actually came together, because those are different stories.

## Timeline

**Fri Aug 28 to Wed Sep 2, 2026: design week.**
Before any code, I spent the week studying the stack I wanted to prove:
PHP without a framework, Go with nothing but the standard library, plus
data structures and algorithms work. The deliverable of that week was a
written plan: scope, architecture, the shape of the rule DSL, and the
constraints the code had to live inside.

- The engine never touches the database. It takes a rule plus
  transactions and returns a verdict.
- Rules are data (JSON) built from constrained selects, never code.
- Money is integer cents everywhere except display.
- No frameworks on either side: front controller, Twig, PDO in PHP;
  net/http and encoding/json in Go.
- One level of condition grouping, because the point was to finish the
  core loop (build, preview, backtest, save, fire) rather than sprawl.

**Wed Sep 2, 7:13pm: the build.**
The repo starts here. I built the whole thing in one focused evening
with an AI coding agent doing the typing under my direction, committing
at phase gates: schema, engine with tests, the HTTP service, the PHP
shell and dashboard, the rule builder with live preview and backtest,
live fire with the alerts inbox, then a readme and launcher pass.
Tests had to pass before the next gate opened.

**Wed 7:47pm to Thu 12:02am: finding the product.**
Using it as it came together reshaped it: plainer copy with the emoji
and decoration stripped out, a live match count added to the preview,
and the scope decision to go coffee-only (homemade vs cafe, plus the
homemade streak) instead of generic budget categories.

**Thu 1:27am: dogfooding.**
A session of using it like a user, then fixing what use revealed: the
add-a-cup form became a disclosure instead of a wall of fields, meters
started reading their thresholds from budget rules instead of hardcoded
defaults, rules began evaluating on save and resume so a rule born
already violated fires on the spot, alerts got dismissals that keep
their dedupe slot, and the vocabulary and typography got quieter.

## On AI assistance

Most of the code in this repo was generated by an AI agent working to
the plan. What is mine: the scope, the architecture, the constraints,
the tradeoffs, the phase gates, the review of everything that landed,
and the bug hunts. Three date and time bugs made it into the build and
were caught by my gates and live verification, not by luck:

- XAMPP's php.ini ships Europe/Berlin while MySQL ran on the Eastern
  clock, and the seeder happily wrote future-dated transactions. One
  timezone is now pinned in the bootstrap, and dates are passed
  explicitly into SQL instead of trusting CURDATE().
- PHP's createFromFormat fills unparsed fields with the current time,
  so "today" parsed as today-at-19:41 and validation rejected every cup
  as future-dated. The `!` format prefix zeroes them.
- A seed run that straddled midnight let three separate passes each
  re-read the clock, and a bought cup ended up inside a guaranteed
  clean streak window. The seed now anchors today once at the top.

Building with an agent is how I expect to work. The engineering that
matters moved up a level: deciding what to build, holding the quality
gates, and verifying that what landed is what was meant.

## Reading the timestamps

The commit history shows execution, not effort. A week of design made
one evening of building enough, and a night of dogfooding made it
usable. If you are evaluating how I work, that sequence is the claim:
plan first, gate every phase, execute hard, then use the thing and fix
what it tells you.
